I've been profiling Canvas AI on a demo site and ran into the same architectural concerns described here. Sharing some measurements in case they're useful for prioritizing the improvements. Setup: 15-component Canvas page, 8 ai_context items configured, Anthropic provider. Instrumented the full agent loop to measure token usage, latency, and call counts per edit type. Findings: 1. Context re-injection is the largest single cost. On a multi-loop agent (e.g. page_builder running 3 loops), the full ai_context block re-appends on every BuildSystemPromptEvent dispatch. On a 15-component page, that's roughly 52% of total tokens spent on content the model has already seen. [#3582288] on ai_context adds a loop_aware flag that skips re-injection on loop > 0. MR !114 is in review. 2. Most common edits don't need the LLM at all. Categorizing 6 weeks of edits from the demo site, approximately 60% resolve to deterministic prop updates — changing a heading, swapping a color token, toggling visibility. These are pattern-matchable without an LLM call, falling back to the AI pipeline for the remaining 40% (layout changes, content generation, multi-component operations). 3. The orchestrator context problem scales with page size. On a 15-component page, a single heading edit sends roughly 111K tokens through the full pipeline. The orchestrator passes the user's input to the sub-agent, which re-fetches page state and context independently. Based on our measurements, scoping context to the affected region (rather than full layout) could reduce the payload by approximately 79%. These observations align with both the proposed directions here and d34dman's points about slimming context aggressively and making actions atomic. The "predictable identifiers" pattern d34dman describes maps well to the component instance IDs that Canvas already assigns — those appear stable enough in our testing to reference across planning and execution steps without round-trips. Profiling methodology: token counts via provider API response metadata, latency via PHP microtime around the AgentRunner call, N=5 runs per edit type with median reported. Happy to share the benchmark scripts or detailed per-operation breakdowns if that would help the discussion. We also prototyped a deterministic handler for the pattern-matchable edits and can share the approach if it would be useful. Disclosure: AI tools assisted development of the prototype; architecture and testing were human-directed.

Filing note: This is a new issue, not a comment on an existing one. Create the issue first, then push the architecture-di-config branch as a merge request against 1.0.x. The companion test issue (#8 below) depends on this — file and note the dependency.

Problem statement

The initial commit ships working code, but the module's architecture does not yet meet Drupal contrib standards in several areas:

  • All cron logic lives as procedural code in the .module file with static \Drupal:: calls, no error handling, and a loop bug where only the last monitored page's data is ever saved.
  • hook_cron() and hook_mail() remain as procedural functions rather than using the #[Hook] attribute pattern already established by the module's other hook classes.
  • The presave hook calls an AI agent to decide whether a Canvas page passes performance benchmarks, then regex-parses JSON from free-form LLM output to make the pass/fail decision. This makes the core behavioral decision non-deterministic, untestable, and fragile to LLM output variation.
  • Hook classes use static \Drupal:: calls instead of constructor-injected services.
  • No *.services.yml — hook classes are not registered as services.
  • No config schema and no default config, so drush config:inspect reports a missing schema.
  • The GoogleAnalytics AiFunctionCall plugin is missing the plugin.manager.ai_data_type_converter argument in ::create() (the parent FunctionCallBase::create() passes this but the override omits it). It also has no credential validation, no try/catch, and uses a static \Drupal::logger() call instead of an injected logger.
  • No composer.json for drupal.org packaging.
  • The service account credentials JSON is uploaded to public://, making it publicly downloadable.
  • The helper function get_monitored_pages() is unprefixed.
  • The agent config references ai_context tools but does not declare ai_context as a dependency.
  • No hook_uninstall() — state entries persist after uninstall.

Steps to reproduce

  • Install the module on a Drupal CMS 2.0 / Drupal 11 site.
  • Run drush config:inspect ai_google_analytics.settings — reports missing schema.
  • Configure a service account and run cron with multiple monitored Canvas pages — only the last page receives GA data.
  • Trigger a presave with the LLM returning unexpected output format — pass/fail decision silently misbehaves.
  • Check the uploaded credentials file — stored under public:// and accessible without authentication.

Proposed resolution

This merge request addresses the issues through seven areas of changes:

1. Extract cron logic to GoogleAnalyticsCronService — new injectable service with try/catch per page, fixes the cron loop bug.

2. Migrate all procedural hooks to OOP — hook_cron() and hook_mail() moved from .module to GoogleAnalyticsHooks with #[Hook] attributes. The .module file is reduced to just the @file docblock.

3. Replace non-deterministic LLM pass/fail with BenchmarkEvaluator — deterministic PHP comparison against configurable thresholds. Three global thresholds in config, three nullable float base fields for per-page overrides. The AI agent is called only when a page has already failed, to generate a human-readable summary. Agent failure falls back to deterministic failure text.

4. Introduce ai_google_analytics.services.yml with full DI — GoogleAnalyticsHooks receives nine constructor-injected services. All static \Drupal:: calls in OOP classes removed.

5. Add config schema and default settings.

6. Harden the GoogleAnalytics AiFunctionCall plugin — add missing plugin.manager.ai_data_type_converter argument, replace static \Drupal::logger() with injected LoggerInterface, add credential guards and try/catch, move credentials to private://, fix function prefix, add strict_types.

7. Update agent config and add packaging files — scope agent to summary-only role, enable structured output, declare ai_context dependency, add composer.json and README.md, add hook_uninstall() for state cleanup.

PHPCS: 0 errors (4 non-blocking DrupalPractice warnings — File::load and t() variable).

The companion issue "Add unit tests for BenchmarkEvaluator and presave hook logic" is stacked on this MR. Please merge [#3585742] first.

Two PHPUnit test files covering the BenchmarkEvaluator service and the presave/delete hook logic. Both use UnitTestCase (no Drupal bootstrap required) and are compatible with PHPUnit 11 and PHP 8.3+.

BenchmarkEvaluatorTest — 8 test cases

  • All benchmarks pass
  • All benchmarks fail
  • Single benchmark fails
  • Per-page override takes precedence (lenient)

Usage tracking is intentionally skipped on loops where no context is injected (documented in code comment). - `src/Form/AiContextAgentForm.php` — Adds checkbox UI. Fixed: code comment and form description now accurately describe this as a token optimization trade-off, with guidance on which context types are safer (stable directives) vs. riskier (factual data, format constraints). ### Finding #2 — Architectural single-responsibility (critical) The subscriber was duplicating `AiContextRequestFactory`'s config lookup. Fixed: `findAgentConfig()` is now public. New `isLoopAware()` method encapsulates the check. The subscriber calls `$this->requestFactory->isLoopAware($agentId)` — it no longer reads `ai_context.agents` config or knows the config key name. Grep confirms only two services read this config: the factory (canonical read) and the form (write on save). ### Finding #3 — Config caching (moderate) Fixed: `loop_aware` flag cached in `$this->loopAwareFlags` during `onAgentStarted()`. Title: Skill: agent execution loop semantics (system prompt lifecycle and loop state)

Problem/Motivation

The agent execution loop in ai_agents has semantics that differ from common assumptions about stateless HTTP request handling. The system prompt is rebuilt from scratch each loop iteration, but developers frequently write code that assumes it accumulates. These errors produce code that passes CI and functional testing but behaves incorrectly under multi-loop execution.

Patterns observed while working on [#3582288]:

  • Assuming system prompts accumulate across loops. BuildSystemPromptEvent fires fresh each loop iteration. The system prompt is rebuilt from scratch and passed to the LLM as a separate parameter — it is replaced, not appended to. Code that skips injecting content "because the LLM already has it" is actually removing that content entirely from the LLM's system context.
  • Confusing system prompt presence with conversation history persistence. When content is in the system prompt on loop 0 but absent on loop 1, the LLM retains influence only through its own prior responses in conversation history. This is a fundamentally different (and weaker) form of context retention. Developers treat these as equivalent when they are not.
  • Not understanding the event dispatch sequence. AgentStartedExecutionEvent fires before BuildSystemPromptEvent each loop. The started event provides the loop count and runner ID. Subscribers that need to vary behavior per-loop must capture state from the started event and apply it in the prompt event — they cannot query loop state directly from the prompt event.
  • Duplicating config lookups that a service factory already owns. When subscribers read agent context config directly instead of using the factory's public API, they risk divergence when the config structure changes.

Proposed Resolution

Create a drupal-agent-loop-semantics/SKILL.md skill covering:

  1. The agent execution loop. AgentStartedExecutionEvent → BuildSystemPromptEvent → LLM call → tool execution → repeat. Each iteration rebuilds the system prompt from scratch.
  2. System prompt vs. conversation history. The system prompt is a separate API parameter, replaced each call. Conversation history (user/assistant messages) accumulates. Content in the system prompt on loop 0 is not in the system prompt on loop 1 unless explicitly re-injected.
  3. Loop-aware optimization patterns. When and how to skip system prompt content on subsequent loops. The trade-off: token savings vs. reduced context fidelity. Which types of content are safe to skip (stable directives, tone guidelines) vs. risky (factual data, format constraints, behavior overrides).
  4. Service boundaries for agent config. Use the factory's public API for agent config lookups rather than reading config keys directly.

Why this skill is needed

The existing skills ([#3583217] render pipeline, [#3583218] entities, [#3583219] config) cover Drupal core subsystems. This skill covers the interaction between the agent execution model and subscriber code — specifically, the parts where the system prompt lifecycle differs from what developers expect. These patterns are observable from the public event API but not documented in a way that prevents the common mistakes above.

This is based on patterns observed as a consumer of these APIs. We would welcome review from the ai_agents maintainers to verify accuracy before the skill is drafted.
